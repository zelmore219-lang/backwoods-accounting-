# Firebase Spark setup — no external host

These builds run the accounting engine **inside the Windows application and Android APK**. Firestore holds the authoritative shared ledger and the source transfers. They do not require Firebase Functions, Firebase Hosting, a separate server, an always-on Windows PC, or a Blaze upgrade. No billing settings or live rules have been changed by this build.

## One-time company setup

1. Export backups from existing apps and keep the originals. In Firebase Console, select `backwoodsbrew-e3584-d52a3` → Firestore Database → Rules. Save a copy of the current rules.
2. Review and paste the complete [merged firestore.rules](firestore.rules), then publish it in Firebase Console. It contains the rules supplied in chat plus the private accounting additions. Existing permission logic is preserved in the whitespace-normalized [baseline](firestore.original.rules); the deny-all fallback remains. Do not replace the Console rules with the smaller fragment file.
3. Open Business Accounting and use **Sign in to Firebase** with the same owner login used by the main and vendor apps. The built-in `admin` username is accepted as well as a full Firebase email. On the first company setup, create the Business Accounting owner account and a passphrase of at least 12 characters. That local/business password protects the books and payroll approvals; the Firebase account connects devices. A phone or PC joining an existing cloud ledger retrieves that ledger rather than making another set of books.
4. Open the updated main and vendor apps and sign in as that same Firebase owner. Changed accounting copies send automatically. There is no transfer-link field, export step or send button. Business Accounting checks for source changes about every 30 seconds while open. Your source apps keep their separate accounting.
5. Test one small retail sale and one delivered wholesale invoice, then payments and corrections. Check amounts, source labels and duplicate counts in Business Accounting. Draft wholesale orders are not revenue. Verify source totals and historical-cost warnings before relying on real financial statements.

Use the **same Firebase owner UID** across all three apps. Staff retain their existing source permissions and do not gain consolidated payroll access. The current whole-snapshot sender runs in an open owner source app. Driver/staff changes must first reach that app through the original Firebase sync. Android may pause background apps; a closed app is not promised to upload instantly. On the next normal open, sync resumes automatically. This build is not a paid server-side trigger service.

## How one shared ledger stays consistent

Each installed accounting app uses the existing double-entry, integer-cent engine. Before a shared write it obtains a bounded Firestore server-timestamp lease and refreshes the latest company generation. It publishes immutable, checksummed compressed chunks and moves the authoritative pointer atomically with a document precondition. An interrupted/corrupt generation is rejected. Competing devices cannot replace the complete ledger with an older database generation; source-level conflicting edits still need their existing reconciliation checks. HTTP success is withheld until the cloud posting is confirmed; pending operation IDs prevent a retried expense from posting twice.

Login sessions remain on their device. Windows connection credentials use Windows-account DPAPI; Android credentials use Android Keystore AES-GCM. Refresh/provider secrets are not put in shared database snapshots or GitHub. Before any external payroll write, the pending state is flushed durably so an uncertain provider response cannot silently permit duplicate submission. Live payroll still requires an approved provider/company and verified funding; the build does not itself move money or file taxes.

The main app's preferred feed copies its own ledger. Vendor copies invoices, payments, credits, purchase receipts and captured costs. Existing receiver rules validate duplicates, closed periods, prior payments, missing posted records and historical costs. Business-entered expenses, recipes, pricing, journals, equipment, depreciation and payroll records share the same company ledger. Whole automatic source snapshots are normalized into financial record histories rather than keeping another full cumulative app backup for every sale. Financial posting/reversal and source-record revisions remain in the database.

If both a local profile and Firebase already contain different populated company books, the app stops for a reviewed migration rather than overwriting either. Back up both first. Old plain main-app backup imports and the native main-ledger feed use different IDs; an already populated book cannot silently switch formats.

## Spark limits and test status

The design uses Firestore and existing Firebase Authentication only. Spark's daily read/write and storage limits still apply; it is not unlimited. App metadata polling is throttled, unchanged feeds are skipped, calculation previews do not acquire write leases, retired transfer chunks are cleaned, and the shared ledger retains its current and preceding complete generation. Failed partial uploads may need an administrator cleanup after repeated outages. The current build supports a 64 MB uncompressed accounting database and 40 MB source snapshots; individual attachments are limited to 10 MB. Exceeding a supported size/quota reports an error rather than confirming an incomplete posting. It never automatically enables billing.

Shared posting requires connectivity. Source apps preserve their own offline records; accounting can show cached data after a local login, but a new shared posting is not confirmed offline. Keep independent backups. Phone availability is independent of Windows once Firestore setup is complete; no PC needs to act as a host.

Android Accounting requires Android 7+ on ARM64 or x86-64 and bundles its own Python engine. Users do not install Python on the phone. Main/vendor retain their existing Android 6+ targets. APKs are debug-signed review builds using the previous test signing identity; Windows installers are unsigned. Back up before changing versions or signing keys.

Automated tests include two-device convergence, writer exclusion, corrupt/incomplete generations, failed-commit rollback, durable payroll intent, duplicate request handling, private native bootstrap, session revocation, record-history retention, and existing accounting features. Firestore emulator checks run in the GitHub release workflow. Real company credentials, physical Android/Windows usage and live control totals have not yet been verified. No live Firebase permission change has been made from this workspace.
